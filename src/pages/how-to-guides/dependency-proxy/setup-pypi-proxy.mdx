# Setup PyPI Proxy with DevGuard Dependency Proxy

PyPI is one of the most actively abused package registries for supply chain attacks. The 2022 PyTorch supply chain attack saw attackers publish a malicious `torchtriton` package on PyPI that exfiltrated sensitive data from machines where PyTorch nightly builds were installed — a package that was installed automatically as a dependency. Thousands of similar attacks have followed, exploiting the fact that `pip install` executes code on download by default.

The DevGuard dependency proxy sits between your Python tooling and the upstream PyPI registry, checking every package against the [OSV dataset](https://osv.dev) before it reaches your environment.

- **Registry URL**: `<your-devguard-url>/api/v1/dependency-proxy/pypi/simple`

## Configuration

### Using a configuration file

Create or edit `pip.conf` (Linux/macOS: `~/.config/pip/pip.conf`, Windows: `%APPDATA%\pip\pip.ini`) to permanently redirect all pip installs through DevGuard:

```ini
[global]
index-url = https://<your-devguard-url>/api/v1/dependency-proxy/pypi/simple
trusted-host = <your-devguard-host>
```

### Using environment variables

For CI/CD pipelines or ephemeral environments, set the proxy via environment variables instead. Most systems do not allow installing packages into the system Python, so create and activate a virtual environment first:

```bash
python3 -m venv .venv
. .venv/bin/activate
```

Then point pip at the proxy:

```bash
export PIP_INDEX_URL="https://<your-devguard-url>/api/v1/dependency-proxy/pypi/simple"
export PIP_TRUSTED_HOST="<your-devguard-host>"
pip install requests
```

<Callout type="warning">
  Only set `trusted-host` when connecting to a DevGuard instance with a self-signed certificate. Remove it when using a properly signed TLS certificate in production.
</Callout>

<Callout type="info">
  On startup, the proxy blocks all requests until the malicious package database is fully loaded. This initialization period prevents cache poisoning. See [Cache Management](/how-to-guides/dependency-proxy/cache-management) for details.
</Callout>

## Testing

DevGuard ships a test package that is permanently flagged as malicious for all versions:

```bash
# fake-malicious-pypi-package must be rejected
if pip install fake-malicious-pypi-package; then
  echo "fake-malicious-pypi-package was NOT blocked - check your proxy configuration" >&2
  exit 1
fi

# pip only reports "No matching distribution found" - check that the proxy answered with 403 Forbidden
status=$(curl -s -o /dev/null -w "%{http_code}" "$PIP_INDEX_URL/fake-malicious-pypi-package/")
if [ "$status" != "403" ]; then
  echo "expected 403 Forbidden for fake-malicious-pypi-package, got $status" >&2
  exit 1
fi
```

If the install is blocked, the proxy is working correctly. pip does not show the `403 Forbidden` itself; it only reports `No matching distribution found for fake-malicious-pypi-package`. All other packages in the same environment will resolve normally from the upstream PyPI registry.

### Testing name normalization (PEP 503)

[PEP 503](https://peps.python.org/pep-0503/) defines a project name as case-insensitive, with any run of `-`, `_` or `.` treated as equivalent. `fake-malicious-pypi-package`, `fake_malicious_pypi_package`, `Fake.Malicious.Pypi.Package` and `FAKE--MALICIOUS--PYPI--PACKAGE` all name the same project. A proxy that compares names as raw strings instead of normalizing them first can be bypassed by requesting the malicious package under an equivalent, differently-spelled name.

<Callout type="warning">
  This is a real bypass class, not a hypothetical: firewalls and SBOM scanners that skip PEP 503/440 normalization have shipped with exactly this gap, letting already-identified malware install without a block.
</Callout>

```bash
# every spelling below refers to the same project as fake-malicious-pypi-package
# and must be rejected with 403, proving the proxy normalizes names before matching
for name in fake_malicious_pypi_package \
            Fake.Malicious.Pypi.Package \
            FAKE--MALICIOUS--PYPI--PACKAGE; do
  status=$(curl -s -o /dev/null -w "%{http_code}" "$PIP_INDEX_URL/$name/")
  if [ "$status" != "403" ]; then
    echo "expected 403 Forbidden for $name (equivalent to fake-malicious-pypi-package), got $status" >&2
    exit 1
  fi
done
```

### Testing version normalization (PEP 440)

[PEP 440](https://packaging.python.org/en/latest/specifications/version-specifiers/#version-equality) defines version equality semantically, not textually: `1.0`, `1.0.0`, `1.0.0.0`, `01.0` and `1.00` all denote the exact same version. A release's version on PyPI is just the first spelling that was used, and nothing requires every file attached to that release to repeat the same spelling in its filename - so a proxy that string-compares versions instead of parsing them can be bypassed by a distribution filename that uses a different, equivalent spelling of a flagged version.

DevGuard ships a second test package, `fake-malicious-pypi-package-versioned`, flagged at the specific version `v1.0.0` rather than for all versions, so it can prove version comparison itself is correct. The proxy checks a distribution download against the malicious package database before ever fetching it from upstream, so the file below does not need to exist for this check:

```bash
# every filename below encodes a version equivalent to the flagged v1.0.0
# and must be rejected with 403, proving the proxy compares parsed versions
# rather than raw filename strings
for version in 1.0.0 01.0.0 1.0.0.0; do
  status=$(curl -s -o /dev/null -w "%{http_code}" \
    "${PIP_INDEX_URL%/simple}/packages/aa/bb/fake-malicious-pypi-package-versioned-$version.tar.gz")
  if [ "$status" != "403" ]; then
    echo "expected 403 Forbidden for fake-malicious-pypi-package-versioned==$version (equivalent to the flagged v1.0.0), got $status" >&2
    exit 1
  fi
done
```

<Callout type="info">
  See [Dependency Proxy Security](/explanations/security/dependency-proxy-security) for the full threat model behind name and version normalization.
</Callout>

Thanks a lot to https://github.com/IlyasMakari for bringing this issue to our attention.

### Testing the minimum package age

The [minimum package age](/how-to-guides/dependency-proxy#minimum-package-age) is configured per repository and only applies to requests using the repository's proxy URL, which contains a secret. The proxy removes all files that are too new from the package index, so pip resolves to the newest version that is old enough instead of failing on the download.

To verify it, temporarily set the minimum age to 87600 hours (10 years). `requests==2.32.3` was published in May 2024, so the proxy must reject it, while an unpinned `requests` still resolves to an older version:

<Callout type="info">
  Recent pip versions have their own client-side filter, `--uploaded-prior-to`. If it is set in your pip configuration, pip hides recent versions itself, independent of the proxy. The proxy enforces the minimum age centrally, for every client and without any client configuration.
</Callout>

```bash
# use a fresh virtual environment, so no installed version satisfies the requirement
python3 -m venv .venv-min-age
. .venv-min-age/bin/activate

# set the minimum package age of the repository to 10 years
devguard-scanner curl --token <your-pat-token> -X PUT \
  -d '{"rules":"","minReleaseAge":87600}' \
  https://<your-devguard-url>/api/v1/organizations/<assetName>/config-files/dependency-proxy-configs/

# the repository's PyPI proxy URL applies its settings
PYPI_PROXY=$(devguard-scanner curl --token <your-pat-token> -s \
  https://<your-devguard-url>/api/v1/organizations/<assetName>/dependency-proxy-urls/ \
  | python3 -c 'import json, sys; print(json.load(sys.stdin)["pypi"])')

# requests 2.32.3 is younger than 10 years and must be rejected
if pip install --no-cache-dir --index-url "$PYPI_PROXY" "requests==2.32.3"; then
  echo "requests==2.32.3 was NOT blocked by the minimum package age" >&2
  exit 1
fi

# an unpinned requirement resolves to the newest version that is old enough
pip install --no-cache-dir --index-url "$PYPI_PROXY" requests
python3 -c 'import importlib.metadata as m; print(m.version("requests"))'

# reset the minimum package age
devguard-scanner curl --token <your-pat-token> -X PUT \
  -d '{"rules":"","minReleaseAge":0}' \
  https://<your-devguard-url>/api/v1/organizations/<assetName>/config-files/dependency-proxy-configs/

deactivate
```
