# Multi-Level VEXing for Releases

Most products are not a single image. A Helm chart for example ships an application container, a web frontend, a database
and an identity provider — each scanned separately, each with its own findings. Your customers, however, do
not consume four images. They consume one release.

**Multi-level VEXing** means making the exploitability statement at the level the product is actually shipped
at, while the scanning still happens per component. In DevGuard you do this with a **release asset**: a
repository whose artifact carries no SBOM of its own, but references the SBOMs of the components it bundles.
Findings roll up into it, and one VEX decision there covers the whole product.

<Callout type="info">
  **Asset = repository.** DevGuard's API and CLI call a repository an *asset* — `--assetName`, `/assets/{id}`
  in URLs. "Release asset" is therefore a repository that stands for a release rather than for a Git
  repository. See [DevGuard Hierarchy](/explanations/core-concepts/organization-groups-repos).
</Callout>

<Callout type="info">
  The referenced SBOMs stay live. DevGuard re-fetches each
  [information source](/how-to-guides/vulnerability-management/sync-external-data) periodically, so a rescan of
  a component shows up in the release asset without you re-uploading anything.
</Callout>

## The example

The DevGuard Helm chart bundles four images:

| Component | Source repository |
|---|---|
| `devguard` | API container |
| `devguard-web` | Frontend container |
| `postgresql` | Database |
| `kratos` | Identity provider |

The goal is one release asset, `pkg:oci/devguard-helm-chart`, that shows the findings of all four and can be
vexed once per release.

## Way 1 — Create the release asset in the UI

Good for a first release or a one-off product view.

1. Create a new repository in your group and give it the release's name.
2. Click the External SBOM URLs Card and create your artifact with a valid purl.

![External URLs card](https://raw.githubusercontent.com/l3montree-dev/devguard-web/refs/heads/main/e2e/docs-screenshots/upstream-url-field.png)

3. Paste the public SBOM URL of each component. You find it on the component's repository under
   **Settings/Public URLs**; the shape is:

   ```
   https://api.devguard.org/api/v1/public/{repository-id}/refs/{ref}/artifacts/{purl}/sbom.json/
   ```

![Release Asset creation](https://raw.githubusercontent.com/l3montree-dev/devguard-web/refs/heads/main/e2e/docs-screenshots/create-release-asset.png)

4. Save. The release asset now aggregates the findings of all referenced artifacts.

<Callout type="warning">
  The URLs are pinned to a ref and an image tag. Every new release means new URLs — done by hand this is
  recurring work, which is what Way 2 removes.
</Callout>

## Way 2 — Create the release asset from your pipeline

Let the release pipeline build the URLs. The version numbers are already in the repository — in the DevGuard
Helm chart the API image tag is `Chart.yaml`'s `appVersion` and the frontend tag is `web.image.tag` in
`values.yaml` — so nothing has to be maintained twice.

### Step 1 — Generate the artifact definition from the chart

The SBOM URL of a component is fully determined by three constants (its DevGuard organization, its purl name
and its registry path) plus the tag that the chart pins. Keep the constants in a small script and read the
tags from the chart; the script writes the artifact definition that the upload job posts:

```ts
import { resolve } from "node:path";
import { parse } from "yaml";

// One DevGuard organization ID per component (components can live in
// different organizations, e.g. a separate frontend team).
const backendOrg = "<backend-org-id>";
const frontendOrg = "<frontend-org-id>";

// The release artifact your release asset should be created under.
const releaseArtifactName = "pkg:oci/my-product-helm-chart";

// Template for a component's purl. `{name}` and `{repo}` come from that
// component's entry below, `{tag}` from its resolved image tag.
const purlTemplate = "pkg:oci/{name}?repository_url={repo}&tag={tag}";

// Template for the public SBOM URL. `{org}` and `{ref}` are the
// component's DevGuard organization and ref (its tag with dots replaced
// by dashes), `{purl}` is the percent-encoded purl built above.
const sbomUrlTemplate =
  "https://api.devguard.org/api/v1/public/{org}/refs/{ref}/artifacts/{purl}/sbom.json/";

// The ref DevGuard creates for a scanned tag: dots become dashes, e.g.
// "v1.13.2" -> "v1-13-2".
function slugifyTag(tag: string) {
  return tag.replace(/\./g, "-");
}

const artifacts: Record<
  string,
  { org: string; name: string; repo: string }
> = {
  database: {
    org: backendOrg,
    name: "database",
    repo: "ghcr.io/my-org/my-product/database",
  },
  backend: {
    org: backendOrg,
    name: "backend",
    repo: "ghcr.io/my-org/my-product/backend",
  },
  frontend: {
    org: frontendOrg,
    name: "frontend",
    repo: "ghcr.io/my-org/my-product/frontend",
  },
};

// Reads each component's image tag from wherever your chart pins it.
// Replace the paths/keys below with your chart's actual layout.
async function readTagsFromRepo(repoRoot: string) {
  const chart = parse(await Bun.file(resolve(repoRoot, "Chart.yaml")).text());
  const values = parse(await Bun.file(resolve(repoRoot, "values.yaml")).text());

  const backendTag = chart.appVersion as string;
  const frontendTag = values.frontend.image.tag as string;

  return {
    database: backendTag,
    backend: backendTag,
    frontend: frontendTag,
  };
}

export function buildSBOMUrls(tags: Record<keyof typeof artifacts, string>) {
  return Object.values(artifacts).map(({ org, name, repo }) => {
    const tag = tags[name as keyof typeof artifacts];
    const purl = purlTemplate
      .replace("{name}", name)
      .replace("{repo}", repo)
      .replace("{tag}", tag);
    return sbomUrlTemplate
      .replace("{org}", org)
      .replace("{ref}", slugifyTag(tag))
      .replace("{purl}", encodeURIComponent(purl));
  });
}

export async function buildSBOMArtifact(repoRoot: string) {
  const tags = await readTagsFromRepo(repoRoot);
  return {
    artifactName: releaseArtifactName,
    informationSources: buildSBOMUrls(tags).map((url) => ({ url })),
  };
}

if (import.meta.main) {
  await Bun.write(
    "request-body.json",
    JSON.stringify(await buildSBOMArtifact(repoRoot)) + "\n",
  );
  console.log(`wrote request body to request-body.json`);
}
```

Two details make the URLs work:

- The **ref segment** is the image tag with dots replaced by dashes — `v1.13.2` becomes `v1-13-2`. That is the
  ref DevGuard creates when the component pipeline scans a tag.
- The **purl is percent-encoded** as one path segment, `encodeURIComponent` included for the `pkg:` scheme and
  the query part.

The result is exactly the file the API expects:

```json
{
  "artifactName": "pkg:oci/my-product-helm-chart",
  "informationSources": [
    { "url": "https://api.devguard.org/api/v1/public/<backend-org-id>/refs/v1-13-2/artifacts/pkg%3Aoci%2Fdatabase%3Frepository_url%3Dghcr.io%2Fmy-org%2Fmy-product%2Fdatabase%26tag%3Dv1.13.2/sbom.json/" },
    { "url": "https://api.devguard.org/api/v1/public/<backend-org-id>/refs/v1-13-2/artifacts/pkg%3Aoci%2Fbackend%3Frepository_url%3Dghcr.io%2Fmy-org%2Fmy-product%2Fbackend%26tag%3Dv1.13.2/sbom.json/" },
    { "url": "https://api.devguard.org/api/v1/public/<frontend-org-id>/refs/v1-13-1/artifacts/pkg%3Aoci%2Ffrontend%3Frepository_url%3Dghcr.io%2Fmy-org%2Fmy-product%2Ffrontend%26tag%3Dv1.13.1/sbom.json/" }
  ]
}
```

### Step 2 — Add the upload job

```yaml
upload-sboms:
  runs-on: ubuntu-latest
  steps:
    - name: Checkout code
      uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0
      with:
        persist-credentials: false

    - name: Set up Bun
      uses: oven-sh/setup-bun@0c5077e51419868618aeaa5fe8019c62421857d6 # v2

    - name: Generate SBOM artifact
      working-directory: schema
      run: |
        bun install
        bun run extractSbomUrls

    - name: Create artifact from SBOM URLs
      uses: docker://ghcr.io/l3montree-dev/devguard/scanner:v1.13.3@sha256:b701867e25e0f749ef0b931cddf3e7c1f53700198fa3cf0030d9a70323ba0169 # look for the latest version on github.com/l3montree-dev/devguard/releases
      with:
        entrypoint: /bin/sh
        args: >-
          -c "devguard-scanner curl -X POST -H 'Content-Type: application/json'
          -d $(cat request-body.json) \
          $DEVGUARD_API_URL/api/v1/organizations/$DEVGUARD_ASSET_NAME/refs/${{ github.ref_name }}/artifacts/"
      env:
        DEVGUARD_TOKEN: ${{ secrets.DEVGUARD_TOKEN }}
```

The job needs nothing but a `DEVGUARD_TOKEN` with the **manage** scope and `DEVGUARD_API_URL` /
`DEVGUARD_ASSET_NAME` from the workflow's `env`. `devguard-scanner curl` is a custom `curl` implementation that
signs the request with that token.

The artifact is created under the ref of the running workflow, so each branch or tag of the chart gets its own
set of bundled SBOMs and its own findings.

## Step 3 — Vex the release

Open the release asset. Findings from all four components appear in one list, each labelled with the artifact
it came from. From here everything works as on a normal repository:

- Mark a finding as a false positive or accepted risk — the decision belongs to this release.
- Turn recurring decisions into [VEX rules](/how-to-guides/vex/vex-rules) so the next release inherits them.
- [Export the VEX or CSAF document](/how-to-guides/vex/export-vex) for the release and hand it to your
  customers — one document for the whole product, not four.
