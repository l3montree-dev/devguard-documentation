# CSAF & VEX Standards

<Tooltip><TooltipTrigger asChild><span className="underline decoration-dotted decoration-yellow-400 decoration-1 underline-offset-4 cursor-pointer">VEX</span></TooltipTrigger><TooltipContent><p>Vulnerability Exploitability eXchange - Vulnerability impact assessments</p></TooltipContent></Tooltip> is a
concept: a machine-readable statement about whether a vulnerability affects a specific product. It is
implemented by three different specifications, and they are not interchangeable. This page explains what
distinguishes them, so you can choose what to publish and know what to expect when consuming someone else's.

If you have not yet met the concept, start with
[What is a VEX Report](/explanations/vulnerability-management/what-is-vex) — it covers the four statuses and
the five justifications that all three formats share.

## What is CSAF?

<Tooltip><TooltipTrigger asChild><span className="underline decoration-dotted decoration-yellow-400 decoration-1 underline-offset-4 cursor-pointer">CSAF</span></TooltipTrigger><TooltipContent><p>Common Security Advisory Framework - Machine-readable security advisories</p></TooltipContent></Tooltip> (Common
Security Advisory Framework)[^1] is an OASIS standard for machine-readable security advisories. Where earlier
advisories were prose in an HTML page or a PDF, CSAF defines a strict JSON schema so that a consumer's tooling
can process an advisory without a human reading it.

CSAF is broader than VEX. A CSAF document consists of:

- **Document metadata** — publisher identity, TLP classification, tracking id, and a full revision history
- **A product tree** — the products and versions the advisory concerns, and how they relate to each other
- **Vulnerabilities** — CVE identifiers, per-product status, remediations, and scores

VEX is one *profile* of CSAF, indicated by the `csaf_vex` document category. A formal disclosure of a
vulnerability in your own software uses a different profile, `csaf_security_advisory`. DevGuard produces both.

The part of CSAF that has no counterpart in the other formats is its **distribution model**: a vendor
publishes a `provider-metadata.json` at a well-known location, aggregators discover it, and every advisory is
served alongside an OpenPGP signature and checksums. Consumers can therefore verify not only the content but
its authorship. This is what makes CSAF the format regulators reach for.

## How the three formats differ

The essential difference is **what a statement is about**.

### CSAF VEX is product-centric

CSAF models products and the relationships between them, so a statement can refer to *this component as it is
used inside that product* — an exact dependency path.

```json
{
    "product_tree": {
        "relationships": [
            {
                "category": "default_component_of",
                "product_reference": "pkg:npm/prismjs@1.27.0",
                "relates_to_product_reference": "pkg:oci/devguard-web@main",
                "full_product_name": { "product_id": "CSAFPID-0003" }
            }
        ]
    },
    "vulnerabilities": [
        {
            "cve": "CVE-2024-53382",
            "product_status": { "known_not_affected": ["CSAFPID-0003"] },
            "flags": [
                {
                    "label": "vulnerable_code_not_in_execute_path",
                    "product_ids": ["CSAFPID-0003"]
                }
            ]
        }
    ]
}
```

Note `CSAFPID-0003`: it identifies not prismjs in general, but prismjs *as reached through this specific
chain*. Two different paths to the same package get two different product ids and can carry two different
statuses. The `flags.label` carries the machine-readable justification.

### CycloneDX VEX is component-centric

CycloneDX attaches the assessment to the component itself, inside the SBOM structure.

```json
{
    "vulnerabilities": [
        {
            "id": "CVE-2024-53382",
            "analysis": {
                "state": "false_positive",
                "detail": "The vulnerable function is never called."
            },
            "affects": [{ "ref": "pkg:npm/prismjs@1.27.0" }]
        }
    ]
}
```

This is simpler and more widely supported, but the <Tooltip><TooltipTrigger asChild><span className="underline decoration-dotted decoration-yellow-400 decoration-1 underline-offset-4 cursor-pointer">PURL</span></TooltipTrigger><TooltipContent><p>Package URL - Standardized package identifier</p></TooltipContent></Tooltip> is the whole
identity — there is no way to say "affected via one path, not affected via another". Where DevGuard holds two
different decisions for one component, the CycloneDX export collapses them and keeps the more severe state.

### OpenVEX is minimal

OpenVEX carries statements as a flat list, designed to be small and embeddable anywhere. DevGuard's OpenVEX
export is repository-level: each statement names the product as a whole rather than individual components.

### Choosing

| | CSAF VEX | CycloneDX VEX | OpenVEX |
|---|---|---|---|
| Statement subject | Product + dependency path | Component purl | Product |
| Per-path decisions | yes | no | no |
| Machine-readable justification | yes (`flags.label`) | no | yes (`justification`) |
| Signatures & discovery built in | yes | no | no |
| Scanner support | narrower | broadest | growing |
| Best for | Regulated disclosure, complex supply chains | Everyday tooling interoperability | Lightweight exchange |

<Callout type="info">
  If you need to convey *why* something is not affected in a form machines can act on, publish CSAF or
  OpenVEX. If you need the widest possible tool compatibility, publish CycloneDX VEX — but note it carries your
  reasoning only as free text. DevGuard generates all three from the same decisions, so this is a question of
  what you hand out, not what you record.
</Callout>

## The point of publishing any of them

**Without VEX**, customers see your scan results and assume you are vulnerable. You answer the same
"does CVE-X affect you?" email every quarter, and each of your customers repeats analysis you already did.

**With VEX**, you publish the assessment once in a form their tooling consumes automatically. The analysis
happens where the knowledge is — with you — and propagates downstream instead of being re-derived at every
step of the supply chain.

<Callout type="info" emoji="📋">
    VEX transforms vulnerability management from "list all CVEs" to "explain actual impact" — which is what
    makes it possible to act on the findings that genuinely matter.
</Callout>

This works in both directions. Your suppliers' VEX documents relieve you of the same redundant analysis, which
is why DevGuard consumes upstream sources as well as publishing your own.
